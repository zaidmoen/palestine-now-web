# عقد المصادقة الآمنة

## الحالة الحالية

المنتج الحالي لا يملك خدمة هوية أو جلسات على الخادم، لذلك لا يعرض نموذج تسجيل دخول ولا يحاكي إرسال OTP أو تسجيل الدخول عبر WhatsApp. واجهة تبدو حقيقية بلا تحقق حقيقي تُضعف ثقة المستخدم وقد تجمع بيانات حساسة دون حماية.

## البنية المطلوبة قبل إضافة `/login`

1. **مزود هوية موثوق** يدعم OIDC/OAuth 2.1 أو OTP حقيقيًا مع سجل تدقيق.
2. **خدمة خلفية** تتولى تبادل الرموز؛ لا تُحفظ أسرار المزود أو refresh tokens في حزمة المتصفح.
3. **جلسة آمنة** عبر Cookie بخصائص `HttpOnly`, `Secure`, و`SameSite` مناسبة، مع تدوير معرف الجلسة بعد الدخول.
4. **صلاحيات من الخادم**؛ اختيار المستخدم لدور «طالب» أو «تاجر» لا يمنحه صلاحية دون تحقق من جهة موثوقة.
5. **حماية إساءة الاستخدام** عبر rate limiting، صلاحية قصيرة لرمز OTP، حد للمحاولات، ورسائل خطأ لا تكشف وجود الحساب.
6. **حماية الطلبات** من CSRF عند استخدام cookies، مع تحقق صارم من origin للعمليات الحساسة.
7. **خصوصية قابلة للفهم** تشرح لماذا تُجمع البيانات ومدة الاحتفاظ بها وكيفية حذف الحساب.

## تدفق الحد الأدنى

1. يختار المستخدم طريقة دخول مدعومة فعليًا.
2. ينشئ الخادم طلب المصادقة ويرسل OTP عبر المزود أو يعيد التوجيه إلى OIDC.
3. يتحقق الخادم من النتيجة وينشئ جلسة قصيرة قابلة للإلغاء.
4. يعيد الخادم ملفًا عامًا بالحد الأدنى من البيانات والصلاحيات المصرح بها.
5. تُسجل محاولات الدخول الحساسة دون تسجيل OTP أو كلمات المرور أو الرموز.

## معيار قبول Pull Request المصادقة

- اختبارات تكامل للنجاح، الرمز المنتهي، كثرة المحاولات، تسجيل الخروج، وإلغاء الجلسة.
- لا توجد أسرار في `VITE_*` أو `localStorage` أو سجلات المتصفح.
- لا توجد محاكاة `setTimeout` لمسار دخول يُعرض للمستخدم كأنه حقيقي.
- الصلاحيات تُختبر على الخادم لكل عملية محمية، وليس عند عرض الصفحة فقط.
- فحص الأمان وESLint والاختبارات وبناء الإنتاج ناجحة.
- مراجعة تهديدات مختصرة تغطي الاستيلاء على الحساب، CSRF، XSS، والتعداد عبر رسائل الخطأ.

حتى تتحقق هذه الشروط، تبقى التفضيلات محلية وغير مرتبطة بهوية، ويظل المنتج صريحًا بشأن ذلك.
